# 第一部分　认识公司

## 1.1 使命与文化

### 公司使命【官方】

**激发创造，丰富生活。**

使命不是宣传口号，而是理解业务和判断工作价值的基本背景。新人面对一项任务时，可以从三个问题出发：

1. 这项工作服务的是谁？
2. 它解决了什么真实问题？
3. 最终效果如何被用户或业务感知？

## 1.2 当前官网所列“字节范”【官方】

根据所给字节跳动官网内容，字节范包括以下六项。

### 1. 共同成长

- 相信并认可使命和愿景，基于使命愿景自驱；
- 面对短期波动有耐心、有韧性，共同解决问题；
- 持续学习，不设边界，与组织一起成长。

**新人可观察行为：**

- 主动了解团队目标，而不仅关注分配给自己的任务；
- 遇到困难及时求助、复盘，不因一次失败放弃；
- 将解决过的问题沉淀为文档或工具。

### 2. 始终创业

- 保持创业心态，始终开创而不守成，创新而非依赖资源；
- 敏捷有效，最简化流程，避免简单事情复杂化；
- 对外敏锐谦逊，避免自满或优越感。

**新人可观察行为：**

- 不把“以前一直这样做”当成唯一理由；
- 优先尝试成本可控的最小方案；
- 发现流程问题时提出改进，而不是机械重复。

### 3. 多元兼容

- 欣赏个体多样性，聚焦人的核心特质；
- 具备全球视角，理解不同文化、观点和实践；
- 善意假设，默认开放信任，有效合作。

**新人可观察行为：**

- 不以学校、地域、年龄、职级等标签判断他人；
- 跨团队产生分歧时，先假设对方有其业务背景；
- 在国际化业务中考虑语言、文化和合规差异。

### 4. 坦诚清晰

- 表达真实想法，不怕暴露问题，反对“向上管理”；
- 准确、简洁、直接，少用抽象、模糊、空泛的词；
- 就事论事，理性沟通，避免主观臆测和情绪化表达。

**新人可观察行为：**

- 风险提前说，不在临近截止日期时才暴露问题；
- 用事实、数据和具体案例表达意见；
- 提出问题时同时说明背景、影响和建议。

### 5. 求真务实

- 独立思考，刨根问底，找到本质；
- 直接体验，深入事实，拿一手数据或信息；
- 不自嗨，注重实际效果。

**新人可观察行为：**

- 不只听转述，主动查看产品、数据、代码和用户反馈；
- 对指标口径进行确认，不用模糊数据支撑结论；
- 功能上线后继续观察实际效果。

### 6. 敢为极致

- 敢于为了更好的结果明智地冒险，注重整体 ROI；
- 尝试多种可能性，在更大范围里寻找最优解；
- 追求卓越、高标准，不仅做了，更要做好。

**新人可观察行为：**

- 重要任务至少比较两个可行方案；
- 在质量、成本、速度和风险之间作出明确权衡；
- 不将“已经完成开发”直接等同于“已经创造价值”。

# 第二部分　新人 30—60—90 天参考计划

以下属于**通用 Onboarding 模板**，不是对字节跳动内部流程的断言。

## 2.1 第 0—7 天：建立工作基础

目标：知道团队做什么、自己负责什么、遇到问题找谁。

建议完成：

- [ ] 阅读劳动合同、员工制度、保密和信息安全要求；
- [ ] 完成账号、设备和必要权限配置；
- [ ] 获取团队组织图、业务介绍和文档目录；
- [ ] 明确 Leader、Mentor、HRBP 和主要协作方；
- [ ] 跑通开发、数据或运营工作环境；
- [ ] 整理第一份“已了解内容与待确认问题”清单。

建议产出：

1. 团队业务的一页纸理解；
2. 权限和环境状态表；
3. 前 30 天目标；
4. 尚未解决的问题清单。

## 2.2 第 8—30 天：完成首个闭环

目标：独立完成一个边界清晰、风险较低的任务。

需要做到：

- 理解任务的上游需求和下游使用者；
- 明确验收标准；
- 提前暴露风险；
- 完成交付、验证和结果说明；
- 对过程中的问题做简短复盘。

“完成开发”不等于完成闭环。一个完整任务至少包括：

> 背景确认 → 方案选择 → 实施 → 验证 → 反馈 → 沉淀

## 2.3 第 31—60 天：端到端负责一件事

目标：从任务执行者逐步转向任务负责人。

建议实践：

- 主动组织需求、技术或数据对齐；
- 管理任务的 Owner、时间和依赖；
- 识别上线、合规、数据或协作风险；
- 交付后跟踪业务或用户效果；
- 形成可复用的 SOP、工具或知识文档。

## 2.4 第 61—90 天：形成独立判断

目标：不仅能做事，也能解释为什么这样做。

建议产出：

- 一个流程、性能、质量或协作方面的改进方案；
- 一次面向团队的知识分享；
- 一份阶段复盘；
- 下一阶段目标及其衡量方式。

# 第三部分　通用协作方法

## 3.1 提问模板：BGTA【推荐实践】

提出问题时尽量包含：

1. **Background——背景**：正在做什么；
2. **Goal——目标**：希望达到什么结果；
3. **Tried——已尝试**：查过什么、做过什么、结果如何；
4. **Ask——请求**：具体需要对方提供什么帮助。

示例：

> 我正在处理登录页兼容性问题，目标是在旧版 Android WebView 中正常完成登录。已经排查 CSS 和接口返回，问题只在特定版本复现。想确认团队是否有兼容性基线或对应机型测试环境。

不要只发送“在吗”“这个怎么弄”或没有上下文的截图。

---

## 3.2 文档与消息怎么选择【推荐实践】

### 适合发消息

- 简短确认；
- 单一问题；
- 紧急状态同步；
- 已有文档的补充提醒。

### 适合写文档

- 需要多人理解的背景；
- 有多个可选方案；
- 需要正式决策；
- 内容较长或需要长期沉淀；
- 涉及跨团队协作。

方案类文档可采用：

1. TL;DR；
2. 背景与问题；
3. 目标及衡量方式；
4. 可选方案；
5. 推荐方案及原因；
6. 风险与依赖；
7. 待决策事项；
8. Owner 和截止时间。

“文档先行”可以作为提高协作效率的推荐方式，但是否为团队强制要求，应以内网规范为准。

---

## 3.3 会议最小规范【推荐实践】

### 会前

- 明确会议目标：同步、讨论还是决策；
- 提供议程和必要材料；
- 只邀请确实需要参与的人。

### 会中

- 先说明目标和需要形成的结论；
- 围绕争议点讨论；
- 对跑题内容单独记录；
- 结束前确认结论、Owner 和期限。

### 会后

纪要至少包含：

- 已作出的结论；
- 待办事项；
- Owner；
- 截止时间；
- 尚未解决的问题。

---

## 3.4 复盘不是追责【推荐实践】

推荐采用五步结构：

1. 原定目标是什么；
2. 实际结果是什么；
3. 差异为什么发生；
4. 哪些做法应该保留、停止或开始；
5. 下一步行动是什么，由谁在何时完成。

对应字节范中的“坦诚清晰”和“求真务实”：既不隐瞒问题，也不以主观判断代替事实。

## 4.4 从公开青训营笔记提炼的工程思维

公开的字节跳动青训营笔记以 Go 的排序算法为例，体现了几个值得纳入新人培训的工程原则：

### 1. 没有脱离场景的“最快算法”

性能取决于：

- 数据规模；
- 数据是否有序；
- 重复元素数量；
- 最坏情况是否可接受；
- 实际运行环境。

### 2. 生产算法通常是组合策略

以 pdqsort 为例，它综合使用了：

- 短序列下的插入排序；
- 一般情况下的快速排序；
- 快排表现不佳时的堆排序兜底；
- 针对有序、逆序和大量重复元素的专项优化。

### 3. 理论正确不等于工程最优

工程实现还要关注：

- Benchmark；
- 常见数据模式；
- 最坏情况；
- 降级和兜底；
- 实现复杂度与维护成本。

这可以进一步抽象为研发工作的基本原则：

> **根据场景选择策略，用数据验证效果，为异常情况准备退路。**

# 第五部分　从价值链理解自己的工作

公开的价值链分析文章将产品过程概括为：

> 市场与用户需求 → 业务和需求分析 → 产品设计 → 研发实现 → 服务、运营、营销和销售 → 用户反馈 → 下一轮迭代

这部分可以用于补强 Claude 原稿中过度偏重“工具和流程”的问题。

新人不应只知道“自己负责哪一段代码”，还要回答：

1. 我的上游是谁，应该向我提供什么？
2. 我的下游是谁，需要我交付什么？
3. 我的工作改善了哪个用户或业务指标？
4. 如果这项工作不做，会产生什么影响？
5. 是否有成本更低、效果更好的解决办法？

研发只是价值链中的一个环节。技术人员需要避免把“技术复杂度”直接当成“业务价值”。

# 第七部分　精简版测试题

不建议继续使用原来的 65 题。可以改为“公开知识闭卷＋团队制度开卷”。

## A. 公开知识题

1. 字节跳动的使命是什么？
2. 写出官网当前列出的六项字节范。
3. “不怕暴露问题，准确、简洁、直接”对应哪项字节范？
4. “直接体验，深入事实，拿一手数据”对应哪项字节范？
5. “注重整体 ROI，在更大范围寻找最优解”对应哪项字节范？
6. 2012 年、2017 年、2019 年各有哪项代表事件？
7. 一个完整提问应包含哪些信息？
8. 复盘与追责有什么区别？
9. 为什么研发人员需要理解产品价值链？
10. 为什么不能把 2020 年招聘帖中的福利直接写进当前手册？

## B. 情景题

### 情景一

你发现需求文档中的两个状态互相冲突，但负责人比你资深。你会怎么处理？

**参考要点：**

- 尽快提出，不因职级保持沉默；
- 写明冲突位置、影响和复现条件；
- 先确认自己是否理解正确；
- 给出一个或多个修改建议；
- 就事论事，不使用情绪化表达。

### 情景二

任务要求两周完成，但你的评估是四周。

**参考要点：**

- 拆解工作量并说明估时依据；
- 明确依赖和风险；
- 给出缩小范围、调整优先级、增加资源或延期等选项；
- 说明不同方案的收益和风险；
- 由负责人决策并将结论同步相关方。

### 情景三

上线后错误率突然上升，且可能与刚发布的版本有关。

**参考要点：**

- 先确认影响范围；
- 优先采取可逆的止损措施；
- 按团队机制通知相关负责人；
- 保留日志、时间线和现场信息；
- 恢复后定位根因；
- 形成有 Owner 和期限的改进项。

具体回滚方式和故障等级必须按团队制度回答。

# 第八部分　资料使用建议

## 可作为主要依据

1. **字节跳动官网**：使命、当前字节范、行为准则、大事记；
2. **正式招聘页面**：当前岗位和任职要求；
3. **员工合同及内网制度**：HR、福利、安全、绩效和权限；
4. **团队知识库**：工具、研发、发布和故障流程。

## 只能作为辅助材料

1. 2021 年 GitHub 前端实习 Issue：用于理解历史岗位能力；
2. 2026 届招聘汇总博客：用于构建岗位能力地图；
3. 字节青训营学习笔记：用于讲解工程算法和生产实践；
4. 软件工程学习日志：用于启发文档化和会议协作；
5. 价值链文章：用于帮助新人理解研发上下游。

## 建议排除

- 瑞典户外品牌商业推广文章：与主题无关；
- Multi-Agent 框架文章：与字节 Onboarding 无直接关系，且包含大量未提供原始证据的量化结论；
- 已过期的内推码、个人 QQ、微信和招聘邮箱；
- 没有正文或无法确认来源质量的聚合站内容。
